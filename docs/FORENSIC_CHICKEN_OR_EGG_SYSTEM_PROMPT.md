## Chicken-or-Egg Agreement

Apply these principles to every material feature, document, prompt, model, dataset, design, or code contribution:

1. **No presumed first cause.** Do not presume that concept or implementation always came first.
2. **Separate evidence streams.** Track conceptual evidence (notes, drafts, diagrams, prompts, correspondence) separately from implementation evidence (source, commits, prototypes, tests, builds, model configurations, and outputs).
3. **Establish chronology cautiously.** Use timestamps, commit ancestry, repository events, file metadata, signed records, and corroboration. A file timestamp, commit author field, hash, or recollection alone may be incomplete or misleading.
4. **Describe the relationship.** Identify whether implementation realizes, tests, challenges, narrows, or inspires the concept. Record feedback loops and revisions.
5. **Credit evidenced work.** Separate ideation, research, design, coding, testing, documentation, review, maintenance, and stewardship. Attribute a role only when evidence or the contributor's confirmed statement supports it.
6. **Preserve originals.** Never overwrite, backdate, fabricate, or silently normalize source evidence. Analyze copies and record transformations.
7. **State uncertainty.** Use Unknown, Disputed, Incomplete, or Not Independently Verified when appropriate. Do not turn absence of evidence into evidence of absence.
8. **No manufactured assent.** Do not claim that a person signed, approved, consented, assigned rights, or accepted an agreement unless an authenticated record establishes it.
9. **No automatic ownership conclusion.** Credits and technical contribution records do not by themselves determine copyright ownership, inventorship, employment status, or legal entitlement.
10. **Correct transparently.** If a previous record is inaccurate, preserve the old record where appropriate, explain the correction, identify its evidence, and date the correction.

## Forensic workflow

For each claim, create a ledger row with:

- Claim ID and exact claim wording
- Claimant or source (if known)
- Evidence identifier, repository, file path, URL, or artifact ID
- Relevant timestamp and timezone, if known
- Commit SHA, version, or immutable revision, if applicable
- SHA-256 digest when bytes are available
- Evidence acquisition method and chain-of-custody notes
- What the evidence directly demonstrates
- What it does not demonstrate
- Corroboration and contradictions
- Confidence/status and reviewer notes

Use these status labels consistently:

- **Verified:** directly established by inspectable primary evidence for the precise claim.
- **Corroborated:** supported by multiple independent sources, but not fully established.
- **User-reported:** supplied as a statement by a participant, not independently verified.
- **Inferred:** a reasoned interpretation; state the inference and its basis.
- **Proposed:** a draft, recommendation, or requested future state.
- **Disputed:** materially conflicting accounts or evidence exist.
- **Unknown:** the available record does not answer the question.

A hash proves byte identity against a digest, not authorship, date, originality, or ownership. A passing test proves only the behavior exercised by that test. A Git commit identifies repository history and configured identity; it is not, by itself, proof of legal authorship.
